# Review of the CLI gateway plan

Reviewed 10 October 2026 against the local repository and current official documentation. This is a design review, not a live deployment or security certification.

**Verdict:** the initial plan was a useful architecture sketch, but was not sufficient for a junior engineer to implement safely. Its largest omission was treating provider onboarding as an implementation detail when it is a feasibility dependency. The revised [plan](CLI_AGENT_GATEWAY_PLAN.md) and [implementation specification](CLI_AGENT_GATEWAY_SPEC.md) address the engineering gaps. Provider-specific live validation still needs to happen.

| ID | Severity | Problem in the first plan | Required correction |
| --- | --- | --- | --- |
| R01 | Blocker | A “Connect account” button was proposed without a demonstrated server-side login/callback procedure for each CLI. A callback to localhost in the user's browser does not reach the server's localhost. | Gate G1: prove native remote login, restart and refresh first. Use operator-assisted native login for the private prototype. Customer onboarding remains a separate deliverable. |
| R02 | Blocker | Own-account login was too easy to confuse with permission to run a hosted subscription product. | Track technical entitlement and hosted-product eligibility separately. Provider enablement requires both for customer use; do not scrape tokens or make custom requests with native CLI OAuth tokens. |
| R03 | Critical | An isolated home still contains credentials readable by the CLI process and potentially by its agent tools. Read-only filesystem access does not mean secrets are unreadable. | Gate G2: explicit tool restrictions, clean configuration and an adversarial canary test. A failed gate disables that provider; never solve it by enabling all tools or approval bypass. |
| R04 | Critical | The worker API was unnamed, unauthenticated in the design, and indistinguishable from the browser API. Existing browser requests require a user JWT. | Separate `cli-worker` function with explicit worker authentication and host scoping; retain user authentication on `appraisal`. No project service key on the worker. |
| R05 | Critical | Existing job rows are team-readable. Putting attempt/lease secrets on them would expose worker authority. | Keep CLI leases, host references, connection metadata and prompt snapshots in private tables. Never place CLI fencing tokens in the existing public lease columns. Test direct database access, not just UI masking. |
| R06 | High | Generic prompt requests cannot directly populate the existing report job schema: address, section, model and positive API credential version are required. | Specify the exact appraisal request. Add a conditional API/CLI credential constraint; use a private connection revision. Generic chat is deferred. |
| R07 | High | Lease expiry and cancellation were named but race outcomes were undefined. Killing a local `docker` client may leave the container running. | Define transactional state transitions, a pre-start handshake, durable container identity and cancellation of the container itself. Never automatically requeue ambiguous inference. |
| R08 | High | `poc_finish_job` rejects completion retries, has no CLI fencing, and pruning can erase results before a retry arrives. | New idempotent CLI finalization with a payload digest receipt; preserve section-level lock ordering and the ten-item retention rule. Never recreate a pruned result on retry. |
| R09 | High | A queued job could use edited instructions, switched accounts or newly selected models when it eventually starts. | Snapshot the assembled prompt and configuration at submission, bind the connection revision, and compare it before launch. User edits require a new request ID. |
| R10 | High | “Check ownership” conflicted with existing intentional team history. Admin powers were unspecified. | Explicit matrix: owners control connections/jobs; active teammates read saved reports; team admins cannot use a member's subscription just because they are admins. |
| R11 | High | Browser retries, reloads and timeouts could generate a new UUID and duplicate inference. | A lookup-by-request-ID operation, stable request ID per deliberate submission, and UI recovery without resubmission after reload. |
| R12 | High | Persistent CLI homes and Docker logs could retain prompts beyond report deletion. | No raw output logging; identify native history files in each runtime manifest; enforce cleanup independently of database history pruning; auth volumes excluded from backups. |
| R13 | High | A free account was treated as sufficient for useful report generation. Agent tool defaults, web search, model access and prompt priority differ from existing APIs. | Capability matrix, real Hebrew report evaluation and explicit unsupported-feature errors. CLI text-only mode does not promise web research or PDF parity. |
| R14 | Medium | There was no concrete resource limit, queue capacity, outage policy or operational owner. | Fixed prototype limits and host health checks; drain/rollback/recovery runbook; refuse work when the worker is stale or unavailable. |
| R15 | Medium | Pinned CLIs were recommended without a version/configuration manifest or upgrade test. | Record CLI/image/runtime versions, exact argument arrays, tool policy, auth mode, parser fixtures and cleanup rules. Fail closed on a mismatch. |
| R16 | Medium | No implementation file map or dependency order was given; the unused FastAPI scaffold could become a competing backend. | Keep the active Edge API; add a separate worker package; implement milestones with tests and artifacts specified in the implementation guide. |

**Evidence from this repository**

- `supabase/migrations/20260922084700_initial_web_app.sql` already defines `job_status`, lease fields, idempotency constraints, a task outbox and team-read policies. Do not duplicate these mechanisms or activate two dispatchers for the same job.
- `supabase/migrations/20260926210539_plot_history_retention.sql` keeps ten completed payloads per workspace/section, clears old content and preserves receipts. Its finalization functions acquire the section advisory lock before job row locks.
- `supabase/functions/appraisal/index.ts` verifies user sessions, requires saved API credentials in the current generation branch and uses `poc_finish_job`/`poc_fail_job`.
- `web/src/App.tsx` creates a new UUID inside every current submit and expects synchronous success. Its configured-state and model selectors assume API credentials.
- `web/src/lib/edge.ts` currently treats errors as strings and returns JSON without exposing HTTP status. The new helper must preserve compatibility while supporting typed CLI errors.
- No `supabase/config.toml` was present in the inspected checkout. Local setup and function verification settings must be created and documented explicitly; do not assume the earlier proposal supplied them.

**External evidence and remaining uncertainty**

The native login and hosting distinction is material in [Claude's conditions](https://code.claude.com/docs/en/legal-and-compliance). OpenAI's published third-party plan integration scope is described in [Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source). Neither a successful personal CLI login nor this review is a substitute for confirming the intended customer deployment.

Actual Google login correction, 2026-10-10: the owner's pinned Gemini CLI 0.63.0 was rejected as an unsupported individual Code Assist client and directed to Antigravity. This invalidates the original Gemini free-account assumption for this experiment. Google now uses official Antigravity 1.3.3 under the stable `gemini` provider ID. The owner signed in natively; a fresh synthetic container reused saved authentication and returned the expected marker. G1 remains incomplete beyond this restart check. The initial restricted-network timeout was traced to the Codespaces legacy firewall; the owner-approved narrow rule was applied. All 15 network checks and a fresh restricted native marker request passed. A fake-secret adversarial test observed no leak, file write, tool step or subagent step, but the CLI still advertises 60 tools after applying the official default-component exclusion setting. The wrapper now rejects this configuration. Effective-tool/credential G2 remains unproved. [Antigravity installation and native account flow](https://antigravity.google/docs/cli/install/).

Antigravity documents that headless mode still permits workspace file reads/writes by default. The runner must mount verified deny-only settings read-only, with all supported action namespaces denied. That is necessary but insufficient: prove MCP, hooks, plugins, skills, native credential storage, fresh conversation behavior and egress isolation against the actual binary. Do not reuse Gemini's admin-policy files as evidence of Antigravity enforcement. [Antigravity headless mode](https://antigravity.google/docs/cli/headless/), [permission rules](https://antigravity.google/docs/permissions/).

**What the revised documents do and do not establish**

They specify the application protocol, private data model, state transitions, worker identity, cancellation rules, implementation order and test matrix. A junior engineer can implement those bounded pieces and know the evidence required at each gate. Exact provider versions, a successful remote authentication recipe, enforceable tool settings and hosted-product eligibility remain explicit provider validation tasks. Claiming those were solved on paper would hide the highest risks.
